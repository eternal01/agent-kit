# 代码审查

## 流程
1. 确认需求/计划、审查范围和基准版本；先看变更统计，再读完整 diff。
2. 按需追踪调用方、数据模型、错误路径、并发、权限、配置和迁移；不把审查扩成无关项目审计。
3. 先检查需求或规格符合性，再检查代码质量；不要用风格意见掩盖功能缺失。
4. 核对非预期变更；检查正确性、安全、数据一致性、兼容性、性能、可观测性、测试和回滚。按需寻找同仓库的正常调用方作对照。
5. 对 P0/P1 候选主动寻找反证和保护条件。证据不足时标为待确认，不升级成确定缺陷。
6. 只报告可说明影响与触发条件的问题；每条包含严重级别、文件行号、证据和可操作建议。
7. 按 P0（事故/数据损坏）、P1（高概率严重缺陷）、P2（一般缺陷/测试缺口）、P3（非阻塞维护建议）排序。
8. 给出 `Approve`、`Request changes` 或 `Comment`，列出已验证内容和局限。

没有问题时明确说明“未发现阻塞问题”，不可制造风格意见。需要委派独立审查时使用[审查提示模板](references/reviewer-prompt.md)，只传需求、范围和必要上下文，不传整个会话。
