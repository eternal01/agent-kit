# 对抗性澄清

## 触发
仅在用户明确要求压力测试，或存在会改变验收、关键取舍或授权范围的重大未决问题，且该问题确实阻塞任务、需要多轮澄清时启用。能由查证或一次针对性提问解决的问题，不升级为独立访谈。

涉及安全、权限、生产、数据迁移或不可逆变更本身不是触发条件。范围与验收已确认时，由当前任务 Skill 完成常规风险检查和必要确认；不重复打开已达成的决策，也不因风险标签暂停所有无依赖工作。

## 原则
- 可由代码、文件、工具或外部资料确认的事实由 Agent 查证；只把需要取舍的决策交给用户。
- 将问题组织为设计树；简单任务一次问一个，复杂任务按 frontier 分轮询问当前互不依赖的问题。
- 每个关键分支至少检查一个反例，包括失败路径、边界输入、滥用方式、依赖故障或回滚条件。
- 给出推荐答案及理由，但不替用户决定；“不知道”应转为显式不确定性、原型或最小验证。

## 流程
1. 读取现状和约束，将表述拆成目标、非目标、假设、决策与验收标准。
2. 识别当前 frontier，提出会改变方案的问题，等待用户回答。
3. 根据回答重算设计树，继续追问新暴露的分支，不重复已解决问题。
4. frontier 为空或只剩明确阻塞项时，汇总已确认、假设、待确认、风险、验收标准和下一步。
5. 请用户审核共同理解摘要；未经确认不进入实施。
6. 用户同时要求留档时，先列出拟写入内容，再按[持久化规则](references/persistence.md)记录已确认的术语或普通决策；符合 ADR 门槛的记录遵循 `architecture-decision` 的约定。明确的留档请求即授权所述范围；决策未确认、变更既有结论或扩大写入范围时先等待确认。
