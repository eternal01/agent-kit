# 实施规划

## 前置条件
输入应包含已确认目标、验收条件和关键约束。实施路径可尚未选定；若缺少会改变架构、产品选择或验收条件的关键决策，列出阻塞项并停止，不在计划中暗自补设计。

## 流程
1. 阅读需求、设计、代码结构、测试/构建配置及项目约定。
2. 若用户要求技术实施方案且实施路径未定，先检查配置、复用和局部修改；存在实质取舍时，优先比较最小化改动、折衷方案和长期目标最优方案（注明优化目标）。比较目标覆盖、影响面、成本、风险、验证与回滚，推荐路径并列出切换条件；不可行的档次说明原因，不凑方案。关键取舍待用户确认后再展开详细任务。
3. 确定路径后列影响面：新增、修改、删除的文件及各自职责；保持现有边界，拒绝无关重构。
4. 按依赖顺序拆成可独立验证、可独立评审的交付任务，而非按技术层机械分组；用稳定任务 ID 标注阻塞关系，检查循环和共享状态。
5. 每项任务写清文件、接口、前置依赖、具体步骤、验证命令、预期结果和回滚点。
6. 涉及部署时写清灰度顺序、监控、失败条件和回滚；涉及兼容、数据或大范围机械迁移时，按[迁移与任务依赖](references/migrations.md)补充兼容矩阵、扩展—迁移—收缩，并区分应用回退和数据恢复。
7. 高风险或存在重大歧义时，检查隐含决策、遗漏影响、失败条件和回滚路径；需要对抗性访谈时请用户明确提出。
8. 用户明确要求编写计划，即视为允许在所述范围内产出或写入计划；执行代码修改仍需单独授权。范围、迁移风险或关键决策变化时重新确认。
9. 对照需求逐条检查覆盖度、顺序、接口一致性及占位符；仅在该检查支持时声明计划完整，并列出未验证项。

按任务复杂度选用[实施计划模板](references/template.md)。计划描述“如何做”，不重复大段背景，也不强制逐步骤提交。
