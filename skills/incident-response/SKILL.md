# 生产事故响应

## 边界与授权

帮助团队组织响应，优先保护人员与用户、限制影响、恢复服务并保留证据。默认只提供分析、计划和草拟通报；不得因“事故”“紧急”或生产环境标签而执行部署、回滚、流量切换、数据修改、凭据操作、通知发送或其他生产变更。执行任何此类动作前，确认用户明确授权的系统、操作范围和停止条件；授权不清时只给安全选项并询问。

## 流程

1. 确认当前是否为真实进行中的事故或演练；收集已知症状、影响范围、开始时间、可信指标、已采取动作、限制与负责人。将事实、推断和未知分开；先查现有值班/事件流程，不自创严重级别或替团队宣布事故。
2. 若影响仍在扩大，先提出低风险止损与恢复选项及其副作用、验证信号和回退条件；区分建议与已执行操作。不要等待根因完全确定才讨论可逆的止损方案。
3. 按需参考[响应角色与状态记录](references/response-structure.md)，明确事件指挥、操作执行、计划/记录和沟通职责。资源不足时建议指挥者指定协助者；避免多人并行改变生产系统。
4. 为每项行动写清责任人、依据、风险/依赖、预期信号、超时或失败处理及下一次评估时间。恢复验证使用用户系统中的健康、错误率、延迟、流量或数据完整性指标，不把单一健康端点当作全面恢复证据。
5. 维护按时间排序的已证实事件、决策、变更和结果；记录未成功的缓解尝试，不覆盖历史。对外通报只起草状态、影响、已知/未知和下次更新时间，不猜测根因或恢复时间；发送前由授权人员审核。
6. 需要交接时说明当前影响、负责人、正在执行/等待的动作、最近证据、风险和下一次更新点；取得接手确认后才视为交接完成。
7. 恢复后核对停止条件和残余影响，列出需后续根因分析、数据核验或复盘的事项；不把应急响应扩写成未经请求的正式复盘或修复任务。

## 完成证据

只在指标或责任人确认的信号支持时声明已缓解或恢复。报告采取了什么、由谁执行及证据来源；没有实际操作或指标验证时，明确写为建议或待验证。该 Skill 不替代组织的值班流程、应急指挥制度或授权机制。
