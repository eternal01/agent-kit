# 详细知识点规范

## 目标

详细知识点围绕一个明确的机制、数据结构、语言特性或设计模式，建立从使用到实现、原理、演进和取舍的完整知识体系。它不是快速知识点的扩写，也不是源码摘要。

## 必备主链路

```text
使用与稳定契约
→ 底层表示
→ 关键操作与算法
→ 边界、复杂度与资源
→ 原理与设计约束
→ 设计动机
→ 版本演进
→ 应用取舍
→ 验证实验
```

### 1. 使用与稳定契约

说明：

- 解决什么问题。
- 如何调用或接入。
- 输入、输出、状态和错误语义。
- 使用者可以依赖什么。
- 前置条件和不适用场景。

### 2. 底层表示

落到实际对象、数据结构、字段职责、内存关系、所有权、共享状态或持久化布局。区分抽象概念和实现表示。例如 Slice 是描述符，底层存储由数组承载，不能把 Slice 等同于数组。

### 3. 关键操作与算法

至少展开一个关键操作的完整路径，包括输入、状态变化、调用链、正常分支和与主题相关的异常分支。数据结构主题通常应覆盖查找、更新、增长/收缩、删除或回收；并发主题应覆盖阻塞、唤醒、取消和退出。

### 4. 边界、复杂度与资源

说明时间复杂度、空间成本、分配、复制、局部性、锁竞争、I/O、网络、GC 或其他相关成本。区分理论复杂度和当前实现的实际成本。

### 5. 原理与设计约束

回答“为什么这个行为成立”和“为什么实现需要这些约束”，连接到语言语义、内存模型、调度、一致性、安全、性能或可靠性模型。

### 6. 设计动机

解释实现者为什么选择当前数据结构或算法。证据优先级：官方设计文档/提案 → 维护者说明或源码历史 → 版本实现对比 → 综合推断。无法核验时必须标注“待确认”，不得把推测写成事实。

### 7. 版本演进

只记录影响理解或迁移的重要变化：版本、旧实现、当前实现、变化原因、行为影响、迁移注意事项和当前基线。没有显著变化时明确写“暂无已核验的重大变化”。

### 8. 应用取舍

单独区分：

- **实现者取舍**：为什么组件内部采用这种方案。
- **使用者取舍**：在什么业务和系统约束下采用、避免或替换该机制。

至少比较一个合理替代方案，使用一致维度：访问模式、复杂度、局部性、分配、并发、可靠性、可维护性、运维成本和退出成本。

### 9. 验证实验

至少提供一个最小示例和一个边界反例或实验，并写明：前置条件、执行方式、预期现象、观测指标和结论边界。不得虚构实验结果。

## 证据标记

正文中明确区分：

- **规范承诺**：语言、协议或标准明确保证。
- **当前实现**：绑定具体版本、Tag、Commit 或源码位置。
- **历史事实**：发行说明、提案、源码历史或维护者记录。
- **官方设计理由**：官方文档或维护者明确说明。
- **综合推断**：由多个实现证据推导出的解释，附置信度。
- **待确认**：已有线索但证据不足。

关键结论应在附近放来源；文末保留完整来源、版本、发布日期和访问日期。

## 条件章节

以下章节按主题添加，不得为了凑结构虚构内容：

- 并发与内存模型
- 失败、恢复与一致性
- 安全与权限
- 观测、测试与性能
- 迁移、兼容与回滚

## 完成检查

- [ ] 是否从真实使用入口开始？
- [ ] 是否说明稳定契约与实现细节的边界？
- [ ] 是否展示真实底层表示和字段职责？
- [ ] 是否完整展开至少一个关键操作？
- [ ] 是否说明复杂度和主要资源成本？
- [ ] 是否解释设计约束和设计动机？
- [ ] 是否核验重要版本演进，或明确没有核验到？
- [ ] 是否区分实现者取舍和使用者取舍？
- [ ] 是否比较替代方案及明确优缺点？
- [ ] 是否有可执行示例、反例或实验？
- [ ] 是否标记规范、实现、历史、推断和待确认内容？
- [ ] 是否与速查笔记、实验、源码阅读或 ADR 建立关系？

## 来源核验停止条件

完成以下步骤后仍找不到更强证据，可以停止检索并标记未知：

1. 检查规范、官方文档、发行说明和官方源码。
2. 对版本变化检查 Proposal、设计文档、源码历史或维护者说明。
3. 进行最多两轮有针对性的补充检索，避免泛化搜索。
4. 若仍无证据，写明“待确认”，不要继续用低质量来源填补空白。
