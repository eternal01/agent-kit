# 软件实施

## 流程
1. 阅读目标、验收标准、相关代码和项目规则；确认修改边界。关键要求缺失时先询问。
2. 高风险或存在重大歧义时，先检查失败路径、隐含假设和回滚条件；需要独立压力测试时请用户明确提出。
3. 用户明确要求实施已确认需求或计划，即视为允许修改所述范围。安装依赖、运行迁移、执行破坏性操作、扩大范围或改变关键方案前需单独确认。
4. 对行为变更先建立最小失败测试；纯配置、文档或无法自动化时说明替代验证。
5. 在理解相关调用链后按[最小充分变更决策梯](references/minimal-change.md)选择方案；进入新增能力层时说明更简单路径为何不足。
6. 进行满足当前要求的最小修改，沿用项目模式；不夹带无关重构、依赖升级或格式化。
7. 每个可观察行为完成一次“失败测试 → 最小实现 → 通过测试 → 整理”循环。
8. 运行最小相关验证，再按影响范围运行类型检查、静态检查、完整测试或构建。
9. 检查 diff 是否仅包含预期文件、是否遗漏配置/迁移/文档；有真实取舍时报告采用与未采用路径、修改文件/新增依赖/新增公开接口及保护项证据。

测试方法见[测试与变更原则](references/testing.md)。遇到未知失败转用 `systematic-debugging`；完成声明遵循公共完成证据规则。
