# 测试与变更原则

## 测试层级
- **单元测试**：纯业务规则、边界值和错误分支。
- **契约/集成测试**：数据库、队列、外部 API、序列化及模块接口。
- **端到端测试**：少量关键用户链路，不重复覆盖所有组合。

## 行为变更循环
1. 写一个能解释目标行为的测试并确认它因预期原因失败。
2. 写使其通过的最少代码。
3. 运行相关测试，确认没有回归。
4. 在测试保护下整理重复和命名。

测试观察公开行为，优先沿用项目已有可测试边界，避免把实现细节和大量 mock 固化。修复缺陷时，回归测试应在撤销修复后失败、恢复修复后通过；在隔离副本或可控补丁中验证，不覆盖用户未提交改动。遵循仓库已有命令和测试风格。

## 测试质量反例

| 反例 | 问题 | 替代验证 |
|---|---|---|
| 期望值重复被测算法，或直接调用被测函数生成 | 实现与测试可能共享同一个错误 | 使用规格、人工独立推导或已知正确样例；例如 100 元折扣 20% 的期望值固定为 80 |
| 只断言内部私有方法的调用顺序或 mock 次数 | 重构会破坏测试，却未必影响外部行为 | 在公开接口断言结果、错误契约和必要副作用；只有顺序本身是契约时才检查顺序 |
| 空断言、吞掉异常，或修复前同样通过 | 测试不能识别目标缺陷 | 在已知错误实现下确认因目标行为而失败；导入失败、超时等无关失败不算有效红灯 |

每次只完成一个可观察行为的红绿循环，避免先批量写完想象中的测试再一次性实现。对复杂逻辑可按项目现状增加性质测试或变异检查，但不为此默认新增依赖。

方法参考：[Matt Pocock tdd](https://github.com/mattpocock/skills/tree/main/skills/engineering/tdd)。
