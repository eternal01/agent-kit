# 方案设计

## 边界
负责“用户得到什么行为、体验及验收结果”，包括已确认总体目标下仍未确定的交互取舍。功能行为已确认、当前只比较代码实施路径或影响面时，入口是 `implementation-planning`，不以是否拆任务为分界。具体产品选型属于 `technology-selection`。

按当前请求选择产物，不因 README 提到服务名、长期隔离目标或未来拆分就扩大为架构设计。功能路径中的长期选项仍围绕功能与体验；相关架构问题只记录为约束或后续待确认项。用户当前要求比较部署边界、数据所有权或系统质量属性时才属于 `system-architecture`；若必须改变这些边界才能满足当前验收，说明阻塞并请求确认，不暗自展开。

## 流程
1. 阅读项目现状、约束和已有约定。
2. 明确目标、非目标、参与者、场景及可验证的成功标准；只追问会影响方案的问题。
3. 识别假设、依赖和风险。复杂需求先拆成可独立交付的范围。
4. 先检查不改变系统、配置现有能力、复用已有实现和局部扩展能否满足场景。功能行为存在实质取舍时，按可行性比较最小改动、折中和长期方案对场景、验收、体验、工期及风险的影响；不凑齐三档，说明不可行路径。以已确认的验收条件推荐当前可交付的方案及切换条件；新增行为的验收尚未确认时，仅将折中或长期路径列为待确认候选，不作为本期承诺；若暂留体验或功能层面的技术债，写明影响与复审触发条件。不比较跨服务边界或拆解代码任务。
5. 描述实现该功能所需的职责、接口、数据流、异常处理和测试思路，细节以足够确认行为为准；跨服务数据所有权交给 `system-architecture`。
6. 高风险或存在重大歧义时，检查反例、失败路径、隐含假设和回滚条件；需要对抗性访谈时请用户明确提出。
7. 用户明确要求产出或写入方案，即视为对所述范围的授权；进入实施、扩大范围或替用户决定关键取舍前仍需确认。
8. 需要留档时按[方案模板](references/template.md)输出。

“最优”必须相对于明确目标、工期及约束，不等于改动最多；不得为凑档次绕过必要安全、兼容或验收要求。遵循 YAGNI；区分“已确认、推断、待确认”，不虚构需求。小改动可直接给简短方案，不强制产出文档。
