# 方案设计

## 边界
把模糊需求收敛为用户场景、业务行为、范围和验收标准。跨服务或部署单元的边界、数据所有权和质量属性交给 `system-architecture`；具体产品选型交给 `technology-selection`；任务拆解交给 `implementation-planning`。

## 流程
1. 阅读项目现状、约束和已有约定。
2. 明确目标、非目标、参与者、场景及可验证的成功标准；只追问会影响方案的问题。
3. 识别假设、依赖和风险。复杂需求先拆成可独立交付的范围。
4. 先检查不改变系统、配置现有能力、复用已有实现和局部扩展能否满足场景。功能行为存在实质取舍时，比较最小化改动、折衷和长期路径对用户场景与验收条件的覆盖、体验差异、改动成本及风险；给出推荐与切换条件。不可行的路径说明原因，不凑方案；代码级任务留给 `implementation-planning`。
5. 描述职责边界、接口、数据流、异常处理和测试思路，细节以足够实施为准。
6. 高风险或存在重大歧义时，检查反例、失败路径、隐含假设和回滚条件；需要对抗性访谈时请用户明确提出。
7. 用户明确要求产出或写入方案，即视为对所述范围的授权；进入实施、扩大范围或替用户决定关键取舍前仍需确认。
8. 需要留档时按[方案模板](references/template.md)输出。

“最优”必须相对于明确目标及约束，不等于改动最多；不得为凑档次绕过必要安全、兼容或验收要求。遵循 YAGNI；区分“已确认、推断、待确认”，不虚构需求。小改动可直接给简短方案，不强制产出文档。
