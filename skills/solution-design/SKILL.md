# 方案设计

## 边界
把模糊需求收敛为可评审的方案。系统边界与质量属性交给 `system-architecture`，具体产品选型交给 `technology-selection`，方案确认后的任务拆解交给 `implementation-planning`。

## 流程
1. 阅读项目现状、约束和已有约定。
2. 明确目标、非目标、参与者、场景及可验证的成功标准；只追问会影响方案的问题。
3. 识别假设、依赖和风险。复杂需求先拆成可独立交付的范围。
4. 存在真实取舍时给出 2～3 个方案，比较复杂度、价值、风险和演进成本；给出推荐理由。
5. 描述职责边界、接口、数据流、异常处理和测试思路，细节以足够实施为准。
6. 高风险或存在重大歧义时，按 `grilling` 规则检查反例、失败路径、隐含假设和回滚条件。
7. 无论是否触发压力测试，都必须先展示方案和修改范围；未经用户明确确认，不得修改文件或进入实施。出现新的重大疑问时暂停并重新确认。
8. 需要留档时按[方案模板](references/template.md)输出。

遵循 YAGNI；区分“已确认、推断、待确认”，不虚构需求。小改动可直接给简短方案，不强制产出文档。
