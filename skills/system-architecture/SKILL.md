# 系统架构设计

## 边界
负责当前请求中的跨服务或部署单元结构及演进：系统边界、依赖、数据所有权、质量属性和运行责任。“长期方案”“复用现有服务”不是单独的触发条件；判断依据是用户是否要求在这些架构维度作取舍。README 中的架构路线图可作为约束，但不能替用户新增设计任务；当前只问功能能否复用组件或配置完成时，保持在 `solution-design` 的范围内。

已定功能的代码实施路径与影响面属于 `implementation-planning`；已确定决策的留档属于 `architecture-decision`；技术产品比较属于 `technology-selection`。

## 流程
1. 明确业务目标、非目标、现状、规模、SLA/SLO、合规、预算和团队约束。
2. 提取最关键的质量属性及可量化场景，避免机械罗列。
3. 定义系统边界、职责、依赖方向、接口、数据流和所有权。
4. 分析容量、一致性、故障隔离、安全、可观测性、部署和运维责任。
5. 架构边界存在实质取舍时，按可行性比较维持现有边界的最小改动、有限调整的折中方案与长期演进方案：评估质量属性、数据所有权、运行责任、工期及迁移/验证/回滚代价。不满足硬约束的路径标为不可行，不凑齐三档；注明当前约束下的推荐、暂留技术债及其影响、复审/偿还触发条件。不重新设计单模块功能行为，也不展开代码任务或单项产品选型。
6. 给出迁移阶段、验证指标、回滚条件、风险与待确认项。
7. 高风险或存在重大歧义时，检查边界、数据所有权、故障隔离、安全滥用和回滚条件；需要对抗性访谈时请用户明确提出。
8. 用户明确要求产出或写入架构文档，即视为对所述范围的授权。架构取舍未确认、涉及不可逆迁移或范围变化时，先等待确认。
9. 需要图示时按 [C4 绘图规范](references/c4.md)输出 Mermaid；按受众只画必要层级。
10. 需要完整文档时使用[架构模板](references/template.md)。

图和正文必须使用一致的名称；无法从证据确认的结论标为假设。
